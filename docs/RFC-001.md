**Status:** Draft
**Author:** Josh

## 1. Problem Statement

People attending weddings, graduations, and other major life events take hundreds of photos and videos on their phones. Currently, collecting these into one place requires either:

- Shared albums (Google Photos, iCloud) that require accounts and app installs
- AirDrop circles that miss Android users
- "Text me your photos" requests that never get followed up on
- Expensive photographer-only galleries that exclude guest perspectives

There is no frictionless, storage-agnostic solution that lets a host say "point your phone here, upload your photos" and have them land directly in the host's own cloud storage.

## 2. Solution

EventVault provides per-event media collection via shareable links and QR codes. Guests upload without creating accounts. Media flows through EventVault's processing pipeline into the host's chosen storage backend.

## 3. User Roles

### Host
- Creates an account (email + password or OAuth)
- Creates and manages events
- Configures storage destination per event
- Views upload dashboard and analytics
- Manages billing

### Guest
- No account required
- Accesses event via link or QR code scan
- Uploads photos and videos from camera roll or live capture
- Optionally provides their name for attribution

### 5.6 Guest Endpoints (no auth required)
```
GET    /api/v1/e/{short_code}                # Resolve event link → event info
POST   /api/v1/e/{short_code}/verify-pin     # Verify guest PIN
POST   /api/v1/e/{short_code}/upload         # Upload file (multipart)

```

## 6. Upload Pipeline

```
Guest device
    │
    ▼
[FastAPI endpoint] ── validate file type, size, event limits
    │
    ▼
[Local temp storage] ── /tmp/eventvault/uploads/{upload_id}
    │
    ▼
[Celery task: process_upload]
    ├── Extract EXIF metadata
    ├── Generate thumbnail (Pillow for images, ffmpeg for video)
    ├── Optimize/compress if configured
    │
    ▼
[Celery task: push_to_storage]
    ├── Read StorageConnection for event
    ├── Decrypt credentials
    ├── Upload to Dropbox / S3 / Managed S3
    ├── Update Upload record with final path
    │
    ▼
[Cleanup] ── Delete temp file
```

### Chunked Upload Flow
1. Client initiates with file metadata → server returns `upload_id`
2. Client sends chunks (5MB default) with chunk index
3. Server stores chunks in temp directory
4. Client calls complete → server reassembles + enqueues processing
5. Server responds with upload status polling URL

## 7. Storage Abstraction

```python
class StorageBackend(ABC):
    @abstractmethod
    async def upload_file(self, local_path: Path, remote_path: str) -> str: ...

    @abstractmethod
    async def delete_file(self, remote_path: str) -> bool: ...

    @abstractmethod
    async def verify_connection(self) -> bool: ...

    @abstractmethod
    async def get_download_url(self, remote_path: str, expires: int) -> str: ...

class S3Backend(StorageBackend): ...
class DropboxBackend(StorageBackend): ...
class ManagedS3Backend(S3Backend): ...  # Same as S3 but we provision the bucket
```

## 8. Security Considerations

- Storage credentials encrypted at rest using Fernet symmetric encryption
- Guest upload endpoints rate-limited (10 uploads/minute per IP)
- File type validation via magic bytes, not just extension
- Virus scanning integration point (ClamAV) for future phase
- CORS locked to app domains
- CSP headers on all responses
- Signed URLs for any media served through EventVault (not direct S3)
